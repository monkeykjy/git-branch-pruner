## 代理结论

**没有发现项目强制设置代理。** 源码、`.npmrc`、VS Code 工作区配置及构建脚本中没有设置代理地址；锁文件没有固定的自定义下载 URL。`.npmrc` 只配置了前后置脚本执行。

`GitService.ts:20` 继承 `process.env`，额外设置语言、禁止终端交互和部分 Windows 变量；没有写入 HTTP/SOCKS 代理，也没有使用 `git -c http.proxy=...`。

当前检查进程中没有 `HTTP_PROXY`、`HTTPS_PROXY`、`ALL_PROXY`、`NO_PROXY` 及其小写形式；当前仓库有效 Git 配置查询没有找到 HTTP/HTTPS、remote 或 core.gitProxy 代理项。`GIT_SSH`、`GIT_SSH_COMMAND` 和 `core.sshCommand` 也未设置。

这些结果只描述本轮终端环境，不能证明另一个已运行的 VS Code 扩展宿主环境相同，也不能排除 SSH 配置、系统代理/VPN、网络策略或特定进程注入。插件会继承外部 Git 使用的环境和配置，因此外部代理设置仍可能影响 fetch；项目没有读取 VS Code 的 `http.proxy` 并传给 Git。

已确认的相关缺陷是 B08：刷新总是等待 fetch，没有超时/取消，失败后的列表也不持续说明数据过期。这可能表现为“不打开代理就一直加载”，但不能据此断定代码强制代理。

## 已复现场景的步骤和观察

1. **B01**：创建名称包含 shell 命令替换的合法本地分支；替换内容仅用于在临时仓库创建标记；调用 `deleteBranches`。观察到标记生成，证明名称被 shell 解释。修复后应删除指定分支且不产生标记。
2. **B02**：创建带独有提交的 feature，切回 main，先验证 `git branch -d` 拒绝，再调用插件删除。观察到 feature 引用消失。不能据此称提交立即永久消失，但正常引用和恢复便利性已经丢失。
3. **B04**：main 与 master 同时存在，当前为 main。读取分支后 master 的 `isMainBranch` 为 false；调用服务删除 master 成功。
4. **B05**：本地 bare remote 命名为 upstream，将 main 推送并设置跟踪。Git 确认 upstream 为 `upstream/main`，插件返回 `exists.remote=false`。
5. **B06**：另一个 worktree 检出 linked。插件返回的名称包含 `+ ` 前缀；这里只验证解析错误，Git 本身仍会拒绝删除被 worktree 使用的分支。
6. **B07**：进入 detached HEAD，读取列表。输出包含括号描述行，而且未标记为当前分支或主分支。
7. **B03**：创建 `topic/<b>demo</b>`，调用真实模板函数。HTML 中包含原始 `<b>` 标签，未进行文本转义，也未生成 CSP。
8. **B08**：预置 origin/main 跟踪引用，在执行层模拟 fetch 失败。确认 `getBranches` 仍先调用 fetch，随后返回 cached remote=true；有警告通知，但返回数据不含更新状态或时间。
9. **B09**：调用服务删除不存在的分支。出现错误通知，但 Promise 正常兑现为 undefined，无法让 provider 汇总失败原因。

## 其他已知限制

- 只处理第一个工作区文件夹；不支持仓库选择。这是当前范围限制，暂不等同于所有单仓库使用都出错。
- 未计算合并状态、ahead/behind，不能把“同名远程存在”解释为同步或可删除。
- 恢复控件时无条件启用所有按钮，会丢失删除按钮原有的禁用条件；无选中项时处理函数直接返回，属于交互问题。
- 错误页缺少重试入口、部分中文场景仍显示英文，输出通道和消息订阅的释放尚未完善。
- 打包依赖缺失与未自动构建等问题见 [开发说明](002.DEVELOPMENT.md)，本轮未做 VSIX 打包验证。
